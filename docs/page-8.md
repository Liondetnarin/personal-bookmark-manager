# 8. เกณฑ์ตรวจงานและการทบทวน

ใช้เป็นรายการตรวจตนเอง ไม่มีคะแนนสอบหรือสถานะผ่านการคัดเลือก

| ด้าน | เกณฑ์ที่ตรวจได้ |
| --- | --- |
| แอป | ล็อกอิน สร้าง ดู กรอง ลบผ่าน UI ได้ และ Backend รองรับ API ตามสเปกทั้งหมด |
| Agent setup | มีกฎและความสามารถใช้ซ้ำที่ใช้งานจริง พร้อมตัวอย่างผลที่เกิดขึ้น |
| API และข้อมูล | Contract ตรงกับโค้ด validation และความสัมพันธ์มีพฤติกรรมชัดเจน |
| Verification | Tests ทำซ้ำได้ ตรวจทั้งกรณีสำเร็จ กรณีผิดพลาด auth และ privacy |
| การตัดสินใจ | อธิบายจุดคลุมเครือ ทางเลือก และผลกระทบได้ |
| กระบวนการเรียนรู้ | หลักฐานจริงตรงกับโค้ด และผู้พัฒนาอธิบายหรือแก้ไขส่วนสำคัญได้ |

## ชุดพฤติกรรมที่ควรพิสูจน์

- ผู้ใช้เข้าถึงข้อมูลของตนเองได้ตาม contract
- token ที่ขาดหาย ไม่ถูกต้อง หรือหมดอายุไม่ผ่านการยืนยันตัวตน
- การตรวจ signature, issuer และ audience เป็นไปตามการออกแบบที่เลือก
- ผู้ใช้ A อ่าน แก้ไข ลบ กรอง หรือเรียกรายการย่อยของผู้ใช้ B ไม่ได้ และ response ไม่เปิดเผยการมีอยู่ของข้อมูล
- ไม่สามารถสร้างหรือย้าย Bookmark เข้า Collection ของผู้อื่น
- ข้อมูลไม่ถูกเปลี่ยนเมื่อคำขอไม่ผ่าน validation หรือ authorization
- PUT, PATCH และการลบ Collection ทำงานตามที่บันทึกไว้
- ผลการบันทึกลง SQL และเส้นทางล็อกอินถึง UI/API ได้รับการตรวจจริง

ระบุให้ชัดว่าส่วนไหนใช้ mocks ส่วนไหนผ่าน token validation จริง และส่วนไหนตรวจด้วยมือ การใช้ test identities สองคนต้องพิสูจน์การแยกข้อมูลได้ ไม่ใช่ seed ไว้เฉย ๆ

## คำถามทบทวน

อธิบายได้หรือไม่ว่าเลือก token แบบใด, ownerId มาจากไหน, tests จะจับบั๊กอะไร และยังมีข้อจำกัดใดบ้าง? ลองแก้ feature เล็ก ๆ ด้วยตนเองแล้วใช้ชุดตรวจงานยืนยันผล
