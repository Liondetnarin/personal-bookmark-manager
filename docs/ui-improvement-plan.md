# แผนปรับ UI ขาว–เขียว

สถานะ: ดำเนินการรอบแรกเสร็จแล้วเมื่อ 2026-09-18

## ข้อสรุปที่ผู้ใช้ยืนยัน

- เป้าหมายหลักคือกลับมาเปิดลิงก์ที่เก็บไว้ โดยเพิ่มลิงก์ใหม่ได้สะดวก
- Desktop เป็นอุปกรณ์หลัก และรองรับ mobile ครบทุกขั้นตอน
- ปรับหน้าตาและขั้นตอนของฟีเจอร์เดิมได้ โดยคง API และกฎข้อมูล
- โทนมินิมอล ขาว–เขียว
- คงสองหน้าหลัก Bookmarks และ Collections รวมทั้ง stack เดิม

## หลักฐานจาก UI ปัจจุบัน

- ธีมมีเขียวเข้มอยู่แล้ว แต่ส่วนหัว บัญชี เมนู และคำอธิบายกินพื้นที่ก่อนรายการ
- ชื่อรายการเปิดรายละเอียดใต้รายการทั้งหมด ทำให้รายการยาวต้องเลื่อนตามหา
- ฟอร์มสร้างแทรกเหนือรายการและดันเนื้อหาลง
- แถวรายการแสดง URL เต็ม บันทึก วันที่ กลุ่ม และปุ่มลบสีแดงพร้อมกัน
- มี loading, empty, error/retry, success และการยืนยันลบอยู่แล้ว ต้องรักษาพฤติกรรมเหล่านี้
- ภาพ Bookmarks ที่มีอยู่บางภาพจับ dropdown ระหว่างเปลี่ยนสถานะ จึงยังไม่ใช้เป็นภาพเปรียบเทียบที่สมบูรณ์

## รูปแบบที่ผู้ใช้ยืนยันใน Q4–Q6

1. ใช้รายการแนวตั้งที่อ่านกวาดตาได้ ชื่อเด่น โดเมนรอง แสดงกลุ่มและบันทึกสั้นตามลำดับความสำคัญ
2. กดชื่อเพื่อเปิดเว็บไซต์ในแท็บใหม่โดยตรง และมีปุ่มรายละเอียดแยกชัดเจน
3. เปิดรายละเอียดในแผงด้านข้างบน desktop และ dialog เต็มจอบน mobile
4. สร้างรายการใน dialog บน desktop และแบบเต็มจอบน mobile เพื่อรักษาตำแหน่งรายการเดิม

ผู้ใช้เลือกข้อ 1 โดยตรง และยืนยันข้อ 2–4 ตามคำแนะนำแล้ว

## ข้อสรุป Q7–Q8 และรายละเอียดสำหรับแผนรวม

ผู้ใช้ยืนยันให้ถามก่อนทิ้งข้อมูลที่กรอกค้าง และคงตัวกรองเดิมหลังบันทึก รายละเอียดต่อไปนี้เป็นข้อเสนอในการนำข้อสรุปไปใช้งาน เพื่อยืนยันพร้อมแผนรวม:

- ฟอร์มที่มีการเปลี่ยนค่าต้องยืนยันก่อนทิ้งข้อมูลเมื่อกดปิด ยกเลิก หรือ Escape; คลิกฉากหลังไม่ปิดฟอร์ม ฟอร์มที่ยังไม่เปลี่ยนปิดได้ทันที ระหว่างส่งคำขอป้องกันการส่งซ้ำและการปิดฟอร์ม
- หลังสร้างสำเร็จคงตัวกรองและหน้าเดิม อัปเดตรายการและจำนวน แสดงข้อความสำเร็จพร้อมปุ่มดูรายละเอียดรายการใหม่จาก ID ที่ API คืนมา โดยไม่เปลี่ยนตัวกรอง หากเพิ่มจากกลุ่มที่เลือกให้ตั้งกลุ่มนั้นเป็นค่าเริ่มต้นที่เปลี่ยนได้ หากรายการใหม่ไม่ตรงตัวกรองให้บอกชัดเจน; หากอยู่หน้าอื่น ให้เปิดรายละเอียดได้แม้รายการใหม่ยังไม่อยู่ในหน้าที่เห็น
- การยืนยันก่อนทิ้งข้อมูลครอบคลุมการปิดฟอร์มภายในแอป; การ refresh/ปิดแท็บอาจใช้คำเตือนมาตรฐานของ browser เมื่อมีข้อมูลค้าง โดยไม่บันทึกข้อมูลฟอร์มลง localStorage อัตโนมัติ

## แนวหน้าจอและภาพรวมที่เสนอ

- รักษาเอกลักษณ์เขียวเข้มเดิม ปรับพื้นให้เป็นขาวกับเทาอ่อน ใช้เขียวอ่อนแสดงตัวเลือกปัจจุบัน สีแดงสงวนสำหรับการลบและ error; ไม่ใช้สีอย่างเดียวสื่อความหมาย
- Desktop: แถบชื่อแอปและบัญชีที่กระชับ เมนูซ้ายสองหน้า พื้นที่หลักเรียงชื่อหน้า/ปุ่มสร้าง → ตัวกรองและจำนวน → รายการ → pagination
- Mobile: ส่วนหัวสั้น เมนูสองหน้าที่แตะง่าย ตัวกรองเต็มความกว้าง รายการหนึ่งคอลัมน์ ฟอร์มและรายละเอียดเต็มจอ
- แถว Bookmark: ชื่อเป็นลิงก์พร้อมสื่อว่าเปิดแท็บใหม่ โดเมนรอง บันทึกย่อและกลุ่ม; ปุ่มรายละเอียดกับลบแยกจากพื้นที่เปิดเว็บไซต์และเข้าถึงได้โดยไม่ต้อง hover
- Collection: ชื่อกลุ่มเปิดรายการลิงก์ของกลุ่มผ่าน route/filter เดิม มีปุ่มรายละเอียดและลบแยก ไม่แสดงจำนวนลิงก์ต่อกลุ่มที่ API ไม่ได้คืนมา
- ภาษาไทยเป็นหลัก ใช้ฟอนต์อ่านง่าย ขนาดข้อความหลักประมาณ 16px และระยะบรรทัดเหมาะกับสระ/วรรณยุกต์; spacing เป็นชุดเดียวกันทั้งแอป เส้นแบ่งบางและเงาเฉพาะพื้นผิวซ้อน
- Modal/drawer ต้องมีชื่อที่โปรแกรมอ่านหน้าจอรับรู้ จัด focus ภายใน และคืน focus ไปปุ่มที่เปิดเมื่อปิด ถ้าปุ่มนั้นหายไปให้คืนไปหัวรายการที่เหมาะสม
- แยกสถานะยังไม่มีข้อมูลออกจากกรองแล้วไม่พบ เก็บค่าฟอร์มเมื่อส่งไม่สำเร็จ มี retry และป้องกันการส่งซ้ำ

## ขอบเขตไฟล์และการเรียนรู้

- `frontend/src/main.tsx`: theme, typography และค่าร่วมของ controls
- `frontend/src/App.tsx`, `AccountPanel.tsx`, `Workspace.tsx`: ส่วนหัว บัญชี navigation และโครง responsive
- `frontend/src/ResourcePage.tsx`: แยกส่วนแสดงรายการ ฟอร์ม และรายละเอียดตามความรับผิดชอบ เพื่อลดความซับซ้อนระหว่างปรับ interaction
- `frontend/e2e/app.spec.mjs`: ปรับการทดสอบตามการเปิดลิงก์/รายละเอียดใหม่ และเพิ่มกรณีข้อมูลค้างกับการคงตัวกรอง
- อธิบายแต่ละช่วงว่าแก้อะไร เหตุใดจึงช่วยผู้ใช้ และใช้หลักฐานใดตรวจผล เก็บผลและภาพสาธิตที่ไม่มีข้อมูลส่วนตัวหลังทำจริง

## ลำดับดำเนินการที่เสนอ

1. ยืนยันแผนรวมนี้ โดยข้อสรุป Q1–Q8 ไม่ต้องถามซ้ำ
2. กำหนดสี ฟอนต์ไทย ระยะห่าง และโครงหน้าจอ พร้อมแบบร่าง desktop/mobile ให้ตรวจ
3. จัดส่วนหัวและ navigation ให้กระชับ ปรับสองหน้ารายการและตัวกรอง
4. ปรับฟอร์ม รายละเอียด feedback และการยืนยันลบตามข้อสรุป
5. ตรวจการใช้งาน keyboard, focus, จอแคบ, ชื่อ/URL/notes ยาว และข้อมูลว่าง/ผิดพลาด
6. รัน typecheck/build และ browser tests ที่ปรับตาม interaction ใหม่ เก็บภาพสาธิตด้วยข้อมูลจำลอง และบันทึกผลจริง

## เกณฑ์ตรวจรับที่เสนอ

- เห็นชื่อหน้า ตัวกรอง ปุ่มสร้าง และเนื้อหารายการโดยไม่ถูกส่วนหัวแย่งพื้นที่เกินจำเป็น
- แยกการเปิดเว็บไซต์ ดูรายละเอียด และลบได้ชัดเจนทั้ง mouse, keyboard และ touch
- การแสดง URL แบบย่อยังเข้าถึง URL เต็มในรายละเอียดได้ และปลายทางจริงไม่ถูกเปลี่ยน
- การลบต้องยืนยันเช่นเดิม ลบกลุ่มแล้วลิงก์คงอยู่ และข้อผิดพลาดไม่ล้างค่าฟอร์ม
- ยกเลิกการทิ้งข้อมูลแล้วกลับมาเห็นค่าที่กรอกครบ ยืนยันทิ้งแล้วล้าง draft และเปิดฟอร์มใหม่ได้
- สร้างสำเร็จแล้วตัวกรองและหน้าที่เลือกไม่เปลี่ยน และดูรายละเอียดรายการที่เพิ่งสร้างได้แม้ไม่ตรงตัวกรอง
- ไม่มี horizontal overflow ที่ความกว้าง 360, 390, 768, 1280 และ 1440 พิกเซล
- รองรับ zoom 200%, focus ที่มองเห็น และ reduced motion; ตรวจ contrast ของคู่สีที่ใช้งานจริง
- ไม่เพิ่ม search สำหรับ Bookmarks, edit UI, sharing, trash, dashboard หรือ deployment ในรอบนี้

## ผลการดำเนินการรอบแรก

- ปรับ shell, navigation และรายการให้กระชับในโทนขาว–เขียว
- เปลี่ยน Bookmark title เป็นลิงก์เปิดแท็บใหม่ และแยกปุ่มรายละเอียด
- ใช้ Drawer บน desktop และ full-screen Dialog บน mobile สำหรับรายละเอียด
- ใช้ Dialog สำหรับฟอร์มสร้าง และถามยืนยันก่อนทิ้งข้อมูลที่กรอกค้าง
- คงตัวกรองเดิมหลังบันทึก และคง API กับกฎข้อมูลเดิม
- ปรับ browser fixtures ให้จับภาพหลังปิด dropdown และตรวจ desktop/mobile
